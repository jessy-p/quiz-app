# Study Loop — Build Plan

Companion to `PROJECT_BRIEF.md` (what to build) — this is the order to build it in. Expected to be edited/checked off as work progresses, unlike the brief.

Ordering principle: front-load "does this feel right" before investing in plumbing, and push open-ended content growth to a phase that doesn't block daily use — you should be able to use the app for real well before the content pipeline or backup sync exist.

## Phase 1 — Skeleton
Next.js + Tailwind scaffold. Reading Lamp tokens wired in as CSS variables / Tailwind config. Static question card rendering one hardcoded question, no answer logic yet. Goal: confirm the visual direction actually renders the way the spec describes before anything else is built on top of it.

## Phase 2 — Core loop
Real `selectNextQuestion` (bias = 0), answer states (correct/wrong, dimming, aria-live), localStorage attempt logging, auto-advance. A small hand-written question set (10-20 questions across a few topics) — enough to exercise the loop, not the real bank. Goal: the app works end to end and is genuinely usable, even if the content is thin.

## Phase 3 — Secondary actions
`ActionSheet` component, three content variants (Reference / Teach Me / Double Check), copy-to-clipboard + toast. Goal: full per-question interaction set complete.

## Phase 4 — PWA + offline
Manifest, service worker, installability, cached question bank for true offline use. Goal: the app already works after Phase 2-3 (online); this phase makes it hold up in the actual use case (elevator, dead zones, one-handed phone use) where connectivity isn't guaranteed.

**Caching strategy decision (so Phase 5/6 data refreshes actually land):**
- Question bank is `import`ed into the JS bundle, not fetched as a separate JSON asset — Next.js content-hashes chunk filenames per build, so a URL-keyed cache doesn't go silently stale the way a hand-cached `/data/questions.json` would.
- **Hand-rolled `public/sw.js`, no Serwist** — the app is a single route with a small bundle, so build-time precache-manifest generation (Serwist's main value) isn't earning its dependency here. Runtime caching only, ~40-50 lines:
  - **Cache-first** for hashed static assets (`_next/static/*`, the JS chunk the question bank lives in) — safe forever, since a content change means a new filename, not a stale hit.
  - **Network-first, cache-as-offline-fallback** for the page navigation request (`/`, unhashed URL) — this is the one thing that must stay network-first, since it's what discovers new deploys (it references whichever hashed chunk names are current).
  - Versioned cache name + `activate` handler that purges old-named caches, so deploys don't leave orphaned cache entries behind.
- `Cache-Control: no-cache, no-store, must-revalidate` on `/sw.js` itself — otherwise the browser's HTTP cache can block the SW update-check from ever seeing a new version.
- `skipWaiting()` + `clients.claim()` in the SW so new deploys activate on next cold open, no "update available" banner — consistent with the app's zero-chrome philosophy. Tradeoff: a rare double-fetch on a tab left open exactly at deploy time, acceptable for single-user use.
- Phase 5's backup POST is already fire-and-forget and doesn't route through the SW cache — no interaction with this.

## Phase 5 — Backup sync
Device token generation, Vercel Blob-backed API route, fire-and-forget POST after each attempt. Goal: protect against localStorage loss (browser reset, PWA reinstall, iOS storage eviction).

**Built against Vercel Blob, not KV** — Vercel KV is deprecated (existing stores migrated to Upstash Redis; new projects are pointed at a Marketplace Redis integration instead). The actual write pattern here — overwrite one JSON snapshot per device, no querying — is a better fit for Blob than Redis anyway: simpler client code, no Redis dependency, and `@vercel/blob` is the current maintained package. Store is `access: "private"`; the blob URL is never returned to the client, only the device token (sent over HTTPS to our own route) and the store's own server-side token can reach it. Overwrite behavior needs both `addRandomSuffix: false` and `allowOverwrite: true` on `put()` — Blob's default is to append a random suffix per write, which would silently accumulate a new object per attempt instead of overwriting.

## Phase 6 — Content pipeline
Three Claude Code slash commands — `/discuss` (interactive planning conversation → confirmed spec), `/generate` (executes the spec by generating each section in parallel, or validates/stages content brought back from elsewhere — either way, adversarial reviewer + fact-checker in parallel, then stage), and `/merge` (staging → live, after a human skim). Then the actual push to grow the bank to real size across whatever topics the user chooses — the topic list isn't fixed (see `PROJECT_BRIEF.md`, and `types/question.ts` where `Topic` is an open string, not an enum). Most open-ended phase — can run in parallel with or after daily use starts, since it doesn't block anything upstream.

**Design note:** originally scoped as 4 separate commands (`generate`/`review`/`factcheck`/`merge`) invoked one at a time, each producing output to inspect before running the next. Revised to 2 (`generate`/`merge`) — review and fact-check ran automatically inside `/generate` rather than as separate manual steps, since per-stage inspection wasn't the actual value being sought. Revised again to 3 (`discuss`/`generate`/`merge`) once the planning step stopped being an ad-hoc conversation and became its own command — see below. The real checkpoints stay upfront (`/discuss`'s confirmed spec) and at the end (a batch-level skim before merge) — not stage-by-stage. Failed/flagged questions are dropped from the batch automatically (flag-and-drop, not auto-fix, see `PROJECT_BRIEF.md`) rather than queued for individual triage.

**`/discuss` — planning became its own command.** Originally just "talk it through in a normal conversation before invoking `/generate`." That worked, but left two things unstructured: no consistent check of actual bank coverage before suggesting topics, and a big ask still had to be capped at ~15 and split across separate future invocations, with the user tracking coverage across rounds themselves. `/discuss` now does both explicitly: reads current per-topic/per-mode counts to ground topic suggestions in real gaps, and **breaks the target into sections** — non-overlapping sub-topics, each sized to the same per-call quality ceiling as before (~15-20), each with its own mode and fact-check decision. Sectioning is what lets a single `/generate` run exceed the old ~15-total cap: sections are generated in parallel, not sequentially, since a non-overlapping sub-topic doesn't need to see another section's output to avoid duplicating it. `/discuss` ends by asking whether to generate now (in Claude Code, via `/generate`) or export a copy-paste prompt for use in a different tool, bringing the output back into `/generate` afterward.

**Context handoff:** `/generate`'s Execute mode reads the confirmed spec straight out of the conversation `/discuss` produced — a fresh session has no way to know what was agreed, so they need to run back-to-back in the same conversation (or `/generate` falls back to a lightweight single-section spec synthesized inline, for small asks that skip `/discuss`). This matters specifically because the generator/reviewer/fact-checker stages run as separate spawned agent calls, which don't inherit the parent conversation's history — the confirmed spec (or its inline fallback) is what actually reaches them, pasted directly into each subagent's prompt.

**Batch size: ~15-20 max, per section, not per invocation.** That's still the ceiling for one generator subagent call's quality — distractor variety, genuine per-item scrutiny, real (not assumed-fine) search verification. What changed is the unit it applies to: a section, not the whole run. The generator gets each section's own dedup list (the existing bank's prompts for that sub-focus) as context, and the adversarial reviewer flags any duplicate/near-duplicate against that list *and* across sections within the same draft batch — plain judgment, no similarity tooling.

**Pipeline efficiency:** adversarial review and fact-check are independent evaluations of the same draft batch (or chunk) — neither needs the other's output — so when both run, they're dispatched as two parallel subagent calls, not sequential ones. In practice review runs far slower than fact-check (tens of minutes vs. a few), so serializing them just adds the faster stage's time for no benefit. When fact-check runs, it always covers the full chunk rather than only what review passed, since gating it on review's verdicts would reintroduce the sequential dependency this is meant to avoid. Every subagent gets the full batch/chunk pasted directly into its prompt, never a file to read, to avoid an extra tool round-trip. Review/fact-check chunk at ~20-25 questions per call regardless of mode — this now applies uniformly, since Execute mode's combined batch (summed across sections) can exceed one call's rigor ceiling just as easily as a large Bring-your-own batch can. What stays intentionally un-optimized: generator/reviewer/(fact-checker, when it runs) remain separate calls, not merged into one — the entire point of separating them is that the generator can't grade its own homework, and collapsing the stages back together to save overhead would undo that.

**Fact-check is conditional, not automatic** (see `PROJECT_BRIEF.md`): mandatory for **time-sensitive** content — anything new or fast-moving enough that training data is likely thin or stale (CCAF is today's clearest example, not a special case baked into the rule itself) — skipped by default for stable technical fundamentals, decided per section/topic. On the first real batch, review caught 2/15 real issues while fact-check caught 0/13 — evidence that fact-check's value is concentrated in domains with thin/stale training data, not universal. Skipping it where it's unlikely to matter cuts real cost (subagent calls, search spend, orchestration) without meaningfully increasing quality risk on that content.

**Bring-your-own content.** `/generate` also accepts already-written question content (pasted, or a file) instead of executing a spec — format-checks it against the schema, then runs the same review/fact-check on it. This is also where content lands after using `/discuss`'s exported prompt externally. The per-section generation cap doesn't apply here (nothing's being invented), but review/fact-check still chunk at the same ~20-25/call as Execute mode. Full mechanics in `.claude/commands/generate.md` and `.claude/commands/discuss.md`.

## Phase 7 — Progress command
`/progress` — reads from the Vercel Blob backup or a copy-pasted attempt log, cross-references against the question bank, reports weakest topics / repeat misses / coverage.

## Phase 8 — Deploy + polish
Vercel deploy. Accessibility re-check against real rendered output (not just the spec's on-paper contrast math). Real-device testing — one-handed use, low light, an actual elevator if you can manage it.

## Phase 9 — Study Hub

**Sequential Study Mode (shipped):** a top-right icon opens a bottom-sheet (`TopicPicker`) listing "Random" plus every topic; picking a topic walks its questions in strict ascending ID order via `useSequentialQuestion` (sibling hook to the random-mode `useNextQuestion`, same `{question, loading, recordAnswer, advance}` shape), with a per-topic cursor (last-shown question ID, not array index) persisted in `storage.ts`. Mode itself (`{type:"random"} | {type:"sequential", topic}`) lives in `StudyModeProvider`'s React Context — needed because the icon has to live in the Server Component root layout (`app/layout.tsx`), several layers above the Client Component that actually selects questions, and Context is what bridges that boundary.

**Study Hub redesign (not yet started):** the same entry point grows from a plain topic picker into a 3-section accordion — Random / Sequential / Progress, in that order — since scope grew past "pick a topic." Renames: `TopicPicker`→`StudyHub`, `StudyModeIcon`→`StudyHubIcon`; topic-list rendering extracted into a new `TopicList`. New: `lib/computeProgress.ts` (pure function, pool + local attempt log → weakest topics / repeat misses / coverage) and `components/ProgressSummary.tsx` — **local-only, no new API route**, since Blob is secondary/non-authoritative and a network round-trip would add nothing a local computation doesn't already have (see below).

**Manual recovery: documented, not built (deliberate).** While designing Progress, found that a localStorage wipe already loses the device token that addresses the Blob backup (`deviceToken.ts` stores it in the same localStorage), so Blob "recovery" doesn't actually self-heal today regardless of what Progress does. Considered building a user-visible/re-enterable sync code + merge-on-write to fix this properly and enable multi-device as a side effect — decided against it: a manual devtools/Blob-dashboard recovery procedure (documented in `PROJECT_BRIEF.md`) already covers the real, rare case (browser reset, reinstall, storage eviction) without the added complexity. Noting this explicitly so it isn't "rediscovered" as a bug later — it's a scoped-out feature, not an oversight.
